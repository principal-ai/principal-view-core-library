# Trail viewer — deployment

How `@principal-ai/principal-view-cli` and `@principal-ai/trail-viewer` are packaged, published, and resolved at runtime so that `npx principal-ai trail view <id>` works on a user's machine without them cloning anything.

Companion to:
- [`TRAIL_VIEWER_MODES.md`](./TRAIL_VIEWER_MODES.md) — what the viewer does at runtime once it's launched.
- [`TRAIL_REPO_PURL_ROLLOUT.md`](https://github.com/principal-ai/industry-themed-file-city-panels) — the schema migration this whole flow rides on.

## TL;DR

Two packages, published independently, glued together by an `optionalDependencies` declaration on the CLI:

- `@principal-ai/principal-view-cli` — CJS-bundled CLI. Adds `trail view <id>`. Has no platform restriction. `optionalDependencies` points at `@principal-ai/trail-viewer`.
- `@principal-ai/trail-viewer` — platform-specific Electrobun bundle. macOS arm64 only today. `os: ["darwin"]`/`cpu: ["arm64"]` in package.json so npm silently skips it on other platforms. Ships a tiny `bin/trail-viewer.cjs` shim that exec's the bundled `.app`.

When a user runs `npx principal-ai trail view <id>`, the CLI's `resolveViewerLaunch` calls `require.resolve('@principal-ai/trail-viewer/bin/trail-viewer.cjs')`. On supported platforms that succeeds and the shim launches the `.app`. On unsupported platforms the optionalDep was never installed, so resolution fails and the CLI exits 2 with a clear message.

Viewer updates ride along with CLI updates today. There is no auto-update path yet — see "Viewer-only updates" below for what would unlock that.

## Package layout

### `packages/cli/`

| File | Purpose |
|---|---|
| `package.json` | `name: @principal-ai/principal-view-cli`, `bin: principal-ai`. Declares `@principal-ai/trail-viewer` under `optionalDependencies`. No `os`/`cpu` restriction — runs anywhere Node 18+ runs. |
| `src/commands/trail.ts` | `trail` command (fetch + publish + view). `cliRequire` is anchored to `process.argv[1]` so resolution works in both the bundled CJS output and dev `.ts` execution. |
| `src/lib/trail-cache.ts` | Reads/writes `~/.principal/trails/...`. |
| `dist/index.cjs` | esbuild CJS bundle, `format: cjs`, `target: node18`. Ships in the tarball. |

### `packages/trail-viewer/`

| File | Purpose |
|---|---|
| `package.json` | `name: @principal-ai/trail-viewer`. `os: ["darwin"]`, `cpu: ["arm64"]` — npm only installs on the matching platform. `bin: { principal-trail-viewer: "bin/trail-viewer.cjs" }`. `files: ["bin", "bundles"]` — only those dirs ship. All runtime deps are `devDependencies` because the `.app` bundles them internally. |
| `bin/trail-viewer.cjs` | Tiny CommonJS shim. Platform-checks (darwin/arm64), exec's `bundles/macos-arm64/trail-viewer.app/Contents/MacOS/launcher` with argv + env passthrough, propagates exit code/signal. |
| `bundles/macos-arm64/trail-viewer.app/` | The 20MB self-extracting Electrobun bundle, generated by `bun run build:bundle`. |
| `scripts/stage-bundle.ts` | `prepack` step. Copies `build/canary-macos-arm64/trail-viewer-canary.app` → `bundles/macos-arm64/trail-viewer.app`. |
| `electrobun.config.ts` | `bundleCEF: false` on every platform (use OS-native webview, smaller artifact). |

## Publishing

### Order

`@principal-ai/trail-viewer` first, then `@principal-ai/principal-view-cli`. The CLI's `optionalDependency` constraint resolves at install time — publishing in this order means users who install the CLI immediately after the publish succeed without a stale-resolution race.

### Commands

```bash
cd packages/trail-viewer
npm publish

cd ../cli
npm publish
```

Both packages have a `prepack` script:

- trail-viewer's `prepack` runs `build:bundle` — `electrobun build --env=canary` + the stage-bundle copy. Ensures the published tarball always carries a freshly-rebuilt `.app`.
- cli's `prepack` runs `build` — `tsc` typecheck + esbuild bundle to `dist/index.cjs`.

There is no automated release pipeline. Per the repo CLAUDE.md, both packages are published manually.

### Version bumps

Bump in `package.json` before publishing:

- Patch (`0.1.0` → `0.1.1`): bug fix, no new feature, no breaking change.
- Minor (`0.1.0` → `0.2.0`): new feature, backward-compatible. **Important for trail-viewer**: a `0.2.0` viewer is *not* installable by an existing CLI (see "Version range semantics" below) — bump CLI's optionalDep range and republish CLI in lockstep.
- Major (`0.x` → `1.0`): breaking. Same lockstep as minor.

Today's versions:
- `@principal-ai/principal-view-cli@0.19.0` — first release with `trail view`.
- `@principal-ai/trail-viewer@0.1.0` — first release.

### Credentials and 2FA

`npm login` (or `NODE_AUTH_TOKEN` env) for the `@principal-ai` scope. If 2FA is on, both `npm publish` calls prompt for an OTP — same code OK if used within the validity window.

## What `npx principal-ai trail view <id>` actually does

1. **npx resolves the CLI**. `npx @principal-ai/principal-view-cli@latest` (or whatever spec) → the latest CLI on the registry, downloaded into npx's cache. If no `@version` is given, npx may reuse a previous cache entry.
2. **npm installs the CLI's deps**, including the optional `@principal-ai/trail-viewer`. On `darwin-arm64` the install succeeds; on other platforms the `os`/`cpu` filter mismatch fires and npm logs `notsup` (not a failure — install completes).
3. **npx invokes `principal-ai trail view <id>`**. The CLI's `viewTrail` function:
   1. Parses the id from the URL.
   2. Tries the cache at `~/.principal/trails/...` (1h TTL); on miss, GETs `https://app.principal-ade.com/api/trails/by-id/<id>` with a GitHub bearer token (resolved via `gh auth token` → `git credential fill` → anonymous), writes the response body to the cache.
   3. Parses the JSON, decides mode (local vs remote — see `TRAIL_VIEWER_MODES.md`).
   4. Calls `resolveViewerLaunch`. The fallback chain:
      - `--viewer-dir <path>` flag — if it has a `bin/trail-viewer.cjs`, treat as installed; if it has a `package.json` only, treat as source.
      - `TRAIL_VIEWER_DIR` env — same.
      - `cliRequire.resolve('@principal-ai/trail-viewer/bin/trail-viewer.cjs')` — finds the optionalDep in `node_modules`.
      - Exit 2 with a "viewer not packaged for this platform" message.
4. **Spawn**. For `installed` launches, the CLI exec's the bin shim directly. For `source` launches (developer override), it `bun start`s in the package dir.
5. **Bin shim runs**. Platform-checks again as a defence-in-depth, then `spawn`s `bundles/macos-arm64/trail-viewer.app/Contents/MacOS/launcher` with argv+env passthrough, propagates exit/signal.
6. **Electrobun self-extracts**. The first run unpacks the compressed `.tar.zst` inside the `.app` to `~/Library/Application Support/ai.principal.trail-viewer/canary/self-extraction/`. Subsequent runs are nearly instant.
7. **Bun host boots**, reads `TRAIL_FILE` / `TRAIL_MODE` / etc., opens the `BrowserWindow`, exposes the RPC the renderer uses to read slices.

The whole chain — invocation to opened window — takes about 5–8 seconds on first run (mostly the self-extract), 1–2 seconds on subsequent runs.

## Version range semantics

The CLI declares `"@principal-ai/trail-viewer": "^0.1.0"`. This is narrower than it looks because semver caret on `0.x` is special-cased:

| Caret | Resolves to |
|---|---|
| `^0.1.0` | `>=0.1.0 <0.2.0` |
| `^0.2.0` | `>=0.2.0 <0.3.0` |
| `^1.2.3` | `>=1.2.3 <2.0.0` |

Practical implications:

- A `trail-viewer@0.1.5` republish reaches existing CLI installs **only when those installs are re-resolved**. npx's cache may serve a stale CLI install indefinitely; users who never run `--prefer-online` may not pick up the new viewer.
- A `trail-viewer@0.2.0` republish is **invisible** to a CLI that ships with `^0.1.0` — even a fresh CLI install resolves to the highest matching `0.1.x`. To ship a 0.2.0 viewer, bump the CLI's range to `^0.2.0` and republish the CLI.
- The cleanest mental model: viewer updates ride along with CLI updates. If you don't republish the CLI, you can't reliably propagate a viewer change.

## Updating

For a viewer-only bug fix (no schema change, no new RPC):
1. Land the fix.
2. Bump trail-viewer to `0.1.<n+1>`. Don't change the CLI's range.
3. Publish trail-viewer.
4. Optional: bump CLI patch + republish to bust npx caches faster. Recommended for visible/important fixes.

For a viewer change that needs CLI changes (new RPC, schema bump, env var):
1. Land both.
2. Bump trail-viewer minor (`0.2.0`).
3. Bump CLI minor and update its `optionalDependencies` range to `^0.2.0`.
4. Publish trail-viewer first, then CLI.

For a CLI-only change:
1. Bump CLI, publish.

## Caveats

### Unsigned `.app`

The bundle is not codesigned or notarized. In practice this is fine for npm-installed users because npm/bun don't set the `com.apple.quarantine` xattr on extracted tarball contents — Gatekeeper only triggers when that bit is present (downloaded via a browser, AirDrop, Mail). The risk surface:

- A user who hand-downloads the tarball from npm via curl and untars it: still no quarantine bit, no Gatekeeper.
- A user who downloads `canary-macos-arm64-trail-viewer-canary.dmg` from the build artifacts (anywhere we eventually host them): quarantined, blocked.
- A user who extracts the `.app` from npm install and copies it elsewhere on disk: still works.

Conclusion: today's npm-only distribution is safe unsigned. Before any release-page distribution, get an Apple Developer ID cert and wire signing + notarization into `electrobun build`.

### Single arch

`darwin-arm64` only. `darwin-x64`, `linux-x64`, `win32-x64` users currently get an `optionalDependencies` skip (no install) and a CLI that exits 2 on `trail view` with a clear message. Acceptable for prototype rollout, not for general release.

### npx caching

npx is good at caching CLI installs. A user running `npx @principal-ai/principal-view-cli trail view ...` repeatedly may stay on a stale version until they pass `--prefer-online`, `--ignore-existing`, or pin a `@<version>` tag. Document this in user-facing instructions: `npx -y --prefer-online @principal-ai/principal-view-cli@latest trail view <id>` for fresh installs.

## Adding another arch

The shim already platform-checks; adding e.g. `linux-x64` is mostly a fan-out:

1. Build `electrobun build --env=canary` on a Linux x64 host (CI matrix).
2. Stage to `bundles/linux-x64/trail-viewer.app/` (or the equivalent AppImage/AppDir Electrobun produces on Linux).
3. Update `bin/trail-viewer.cjs` to map `(linux, x64)` → `bundles/linux-x64/...` with the right launcher path.
4. Either:
   - **Same package, multi-arch**: drop `os`/`cpu` restrictions from `package.json`, ship all arches in one tarball. Pro: one publish. Con: every install pulls every arch (~80MB for four arches).
   - **Per-arch packages, esbuild/biome style**: split into `@principal-ai/trail-viewer-darwin-arm64`, `-linux-x64`, etc., each with `os`/`cpu` filters. The main `@principal-ai/trail-viewer` becomes a tiny shim that requires the right per-arch package. CLI stays as today. Pro: each user only downloads their arch. Con: `n+1` packages to publish in lockstep.

Per-arch packages are the pattern most native-binary npm tools use and is what we should adopt before exiting prototype.

## Viewer-only updates (Electrobun self-update)

Electrobun's build pipeline already produces `update.json` and supports a self-update channel keyed by `baseUrl` in `electrobun.config.ts`. Today `baseUrl` is unset, so the launcher logs `No baseUrl configured, skipping patch generation` on every build.

Wiring this up would let viewer updates flow to users without a CLI republish:

1. Host the canary build artifacts at a stable URL (S3, GitHub Releases, or our own CDN).
2. Set `baseUrl` in `electrobun.config.ts` to that URL.
3. Re-run `electrobun build --env=canary`. The build now generates a patch from the previous version, and `update.json` records the version + URL.
4. The launcher in users' machines, on next start, checks `update.json` against the canary URL and downloads patches in the background.

Tradeoffs:
- Pro: viewer-only fixes ship without a CLI publish. Big win for "viewer broke, CLI is fine" incidents.
- Con: requires hosting infrastructure and a stable URL we control. Code-signing becomes more important — distributing artifacts off npm is exactly the path that triggers Gatekeeper quarantine.
- The signing + hosting setup is mechanical but non-trivial. Not on the path for a prototype rollout; revisit when there's a real "we need to ship a fix without a CLI republish" pain point.

## Local end-to-end test

To verify the publish chain without actually publishing:

```bash
# 1. Build + pack both
cd packages/trail-viewer && npm pack
cd ../cli && npm pack

# 2. Install the tarballs in a scratch dir
SCRATCH=/tmp/principal-cli-scratch
rm -rf "$SCRATCH" && mkdir -p "$SCRATCH" && cd "$SCRATCH"
npm init -y >/dev/null
npm install \
  /path/to/principal-ai-trail-viewer-0.1.0.tgz \
  /path/to/principal-ai-principal-view-cli-0.19.0.tgz

# 3. Run
./node_modules/.bin/principal-ai trail view <id>
```

The chain that runs is exactly what users will hit via `npx`: bin shim resolution, optionalDep, self-extract, RPC handlers. If this works locally, the publish is safe.
